## 2. Criteria

### 2.1 Hard ship-gate threshold (canonical)

```
(chunk_loop_total_ms + sum(perf-startup_named_buckets))  /  cold-CLI Defender-off  <=  1.10x
```

on **paired** same-cell hermetic Mick-corpus measurement.

The numerator is the **engineering-fixable wall** — engine work (`chunk_loop_total_ms` per perf-chunks) plus engineering-controllable startup (named buckets per perf-startup). Excludes the structural-startup residual (see §2.4 for empirical basis).

**Paired** means cold-CLI immediately precedes cold-GUI in the same matrix run with `sdd-standby-purge` between cells (both genuinely cold; not sharing page cache; same Defender state; same disk state). Eliminates inter-matrix CLI variance (sprint band ~25-35s on Mick-corpus).

**Mick-corpus** = `C:\sdd-tests` on Mick's actual dev workstation (302K files, ~36 GiB). Canonical production-corpus per `feedback_perf_ship_gate_absolute_wall_over_ratio`.

### 2.2 Engineering target (during work)

`<=1.05x` engineering-fixable ratio — aim for headroom to absorb matrix variance without false-RED on borderline runs.

### 2.3 Informational reporting

Alongside §2.1 canonical criterion, the matrix runner reports raw walls + the structural-residual breakdown for transparency:

- **Raw cold-GUI wall** (file-watch measurement, what Mick experiences).
- **Raw cold-GUI / cold-CLI ratio** (informational; will be > 1.10x while structural-startup is bounded).
- **Structural-startup cost** = `cold-GUI_wall - chunk_loop_total_ms - sum(perf-startup_named_buckets)` (the eframe/winit/egui residual).
- **Engineering-fixable wall** = `chunk_loop_total_ms + sum(perf-startup_named_buckets)` (the §2.1 numerator).

The raw ratio shows the user-perceived UX impact; the engineering-fixable ratio is the ship gate.

### 2.4 Empirical basis for the carve-out

GUI cold-start has ~8s of structural startup tail (eframe init / winit window creation / egui first-frame rendering / accesskit_windows IPC) that CLI does NOT have. This is empirically confirmed (v0.3.40 Phase 4 matrix on a66f813: 10 named perf-startup buckets sum to 2.151ms while residual is 8.08s — ~4000x ratio of unaccounted-for vs accounted-for startup time).

**Structural-bound startup is NOT engineering-fixable in v0.3.40 scope.** It is queued as v0.3.41 lazy-eframe-init candidate. Until v0.3.41 closes the structural residual, the §2.1 criterion uses the engineering-fixable wall as the load-bearing measurement.

**Fallback ONLY for known pre-instrumentation baseline binaries** (e.g., comparing a v0.3.39 release binary that pre-dates the perf-startup buckets): apply §2.1 with `sum(perf-startup_named_buckets) = 0` plus a documented assumption that structural-startup ≈ baseline residual. Flag in verdict report.

**Current-instrumentation binaries (v0.3.41+) missing perf-startup IS AN ERROR**, not a fallback case — the env var or harvest regex hotfix was not applied (per §7.9 lockstep methodology). Investigate before re-firing; do NOT proceed with sum_named=0 (which would let a false-GREEN slip through if the matrix runner config is broken).

### 2.5 Defender-on cell

Reported informational alongside Defender-off (canonical). Provides real-world reference: Mick's actual scan typically has Defender active.

**Methodology gap rule:** if `Defender-on cell EXCEEDS 1.10x engineering-fixable ratio when Defender-off cell is GREEN <=1.10x`, file a methodology gap per `feedback_dev_loop_matrix_canonical_pr_first` section 12.4. This is the criteria-relative bound: gap fires when matrix-canonical says ship-ready but real-world says not.

## 4. Methodology

### 4.1 File-watch wall measurement

Per design 2026-06-06 12:26 PDT methodology-gap report: matrix runner uses **scan-history JSON mtime + size-stabilization** as scan-end signal, NOT CPU-idle-tail. CPU-idle-tail overstated user-perceived wall by ~20-38s per cell (v0.3.39 file-watch validation: 52.95s vs prior CPU-idle-tail 90.78s = -41.7%).

Algorithm:
- For each `cold-GUI` cell: launch binary; poll for `<data_dir>/scan-history/<scan_id>.json` to appear (200ms polling).
- Once file exists: wait for size-stabilization (1s of unchanged size confirms write complete).
- Parse JSON: verify `scan_id` field exists + `started_at_unix` + `completed_at_unix` + `completed >= started`. (Defense against fast-GUI-crash false-GREEN per quality F1 + codex Cat 1 #1.)
- Wall = elapsed from process launch to size-stabilization.
- 10-min safety timeout.

For `cold-CLI` cells: CLI process exit is canonical scan-end. Validate `$LASTEXITCODE=0` + JSON file exists + parseable + `schema` field present + `groups` field present. (Per `da05506` hotfix; CLI schema is `superdeduper.scan.v2` with `schema` + `groups` top-level, NOT `total_files` / `files_inventory`.)

### 4.2 Engine instrumentation env vars

Set per matrix cell:
- `SUPERDEDUPER_PERF_INSTRUMENT_UPDATE=1` (canonical; perf-chunks + perf-streaming + perf-startup)
- `SUPERDEDUPER_PERF_INSTRUMENT_RAYON=1` (when binary supports; perf-rayon-hash + perf-rayon-hash-worker)
- `SUPERDEDUPER_PERF_INSTRUMENT_CHUNK_EMIT=1` (when binary supports; perf-chunk-emit 6-bucket decomposition per chunk; PR #172+)
- `SUPERDEDUPER_FORCE_IO_THREADS=N` (when binary supports; pins rayon worker count deterministically across CLI + GUI processes; PR #175+; canonical matrix value N=16)
- `SUPERDEDUPER_TEST_DATA_DIR=<output>/hermetic-data` (fresh tempdir per cell)

Harvest regex must EXPLICITLY enumerate each `perf-*:` prefix the engine emits — the generic substring `perf-chunks` does NOT match `perf-chunk-emit` (see §7.9 lockstep methodology). Maintain the regex alternation in lockstep with engine instrumentation PRs.

### 4.3 Reporting

Per cell, report:
- Wall (file-watch measurement).
- Engine-authoritative wall (scan-history JSON `wall_ms`).
- perf-chunks decomposition (chunk_setup_ms + chunk_hash_ms + chunk_emit_ms + chunk_loop_total + chunk_wall_p50/p99).
- perf-streaming (runner_wall_ms + batches + groups_emitted).
- perf-startup 10+ bucket decomposition + residual.
- perf-rayon-hash + perf-rayon-hash-worker (when present; aggregate across chunks).
- **perf-chunk-emit** 6-bucket aggregation across chunks (when present): the 6 bucket fields are emitted in **microseconds**: `checkpoint_save_us` + `checkpoint_record_us` + `tx_send_dup_us` + `tx_try_send_us` + `tx_send_log_us` + `cache_stats_us` → `named_sum_us`. Convert to milliseconds BEFORE comparing to `chunk_emit_ms_total`: `named_sum_ms = named_sum_us / 1000`. Then `residual_ms = chunk_emit_ms_total - named_sum_ms` (sum-conservation invariant). Skew: `max(per_chunk_named_sum_us) / mean(per_chunk_named_sum_us)` → `named_sum_skew_ratio` (burst detector; unit-free ratio so conversion not required). **v0.3.42 semantic shift:** single-chunk pivot (PR #178) makes `chunks_total=1`; perf-chunk-emit fires ONCE per scan = effectively aggregate; skew_ratio loses meaning (1 sample = no skew; informational only). Sum-conservation + dominance checks still work.
- **num_workers** from `perf-rayon-hash` for CLI cell AND GUI cell — **load-bearing env-pin verification** (asymmetric = `SUPERDEDUPER_FORCE_IO_THREADS` not honored OR probe lottery active; flag for Phase 11+ diagnostic).
- **perf-scan-lifecycle** 3-metric framework per process (always-on per PR #177; PERF_METRICS.md canonical):
  - `ttws_ms` — time to walk start (process entry → first walker call; GUI window init residual surfaces here)
  - `ttw_ms` — time to walk (first walker call → walker returns; inventory pass)
  - `ttdd_ms` — time to dedupe (walker returns → scan complete; hash + emit + finalize)
  - `total_ms` — composition-invariant sanity. Per PR #177 implementation, the three phase fields are emitted as DURATIONS (not cumulative timestamps); the invariant compares the raw sum directly: `total_ms ≈ ttws_ms + ttw_ms + ttdd_ms` (small drift from per-phase `Instant::now()` granularity acceptable).
  - `process=cli|gui` for CLI-vs-GUI diff (canonical sprint comparison)
  - **Phase 11+ DIFF test:** paired single CLI+GUI cell on same corpus, same machine, same env pin; diff each metric to localize divergence. Per spec §6 interpretation: TTWS divergence → drill perf-startup + lazy-eframe-init; TTW divergence → walker investigation (rare; possible under USB-class storage); TTDD divergence → drill into hash + emit sub-phases (v0.3.41 Phase 10 surface; v0.3.42 closed via single-chunk pivot).

## 5. Auto-Evaluation

Matrix runner auto-evaluates the **§2.1 canonical engineering-fixable criterion** per cell pair (using values harvested from perf-chunks + perf-startup instrumentation in the same cell):

```
# §2.1 canonical (load-bearing for ship-gate)
engineering_fixable_wall_off = cell2.chunk_loop_total_ms + cell2.sum_perf_startup_named_buckets
ratio_def_off                 = engineering_fixable_wall_off / cell1.wall

engineering_fixable_wall_on  = cell4.chunk_loop_total_ms + cell4.sum_perf_startup_named_buckets
ratio_def_on                  = engineering_fixable_wall_on  / cell3.wall

GREEN  if ratio_def_off <= 1.10
EDGE   if 1.10 < ratio_def_off <= 1.20
RED    if ratio_def_off > 1.20

ERROR  if any cell wall is sentinel -1 (CLI crash OR GUI crash without completed scan)
       OR perf-chunks / perf-startup instrumentation missing on a GUI cell built
         with current instrumentation (= binary regression OR matrix-runner
         config bug; investigate before re-firing).

NOTE: §2.4 fallback (sum_named = 0 + flag for design review) applies ONLY when
the GUI binary is a KNOWN pre-instrumentation baseline (e.g., regression compare
against an earlier release that predates the perf-startup buckets). For
current-instrumentation binaries, missing perf-startup lines IS an error,
not a fallback case.
```

### 5.1 Informational diagnostic ratios (also emitted)

Alongside the canonical §2.1 verdict, the runner emits **raw and structural decomposition** for transparency:

- `raw_ratio_def_off  = cell2.wall / cell1.wall` — user-perceived UX impact (per §2.3)
- `raw_ratio_def_on   = cell4.wall / cell3.wall`
- `structural_startup_cost_off = cell2.wall - cell2.chunk_loop_total_ms - cell2.sum_perf_startup_named_buckets` — eframe/winit/egui residual (per §2.4)
- `structural_startup_cost_on  = cell4.wall - cell4.chunk_loop_total_ms - cell4.sum_perf_startup_named_buckets`

These are emitted for **post-verdict interpretation** (§6) and **methodology gap detection** (§2.5) but do **not** drive GREEN / EDGE / RED labeling.

### 5.2 Defense-in-depth validity gates

Both `cell_wall > 0` AND `scan-history JSON valid` required for non-sentinel wall (per F1 + codex Cat 1 #1 layered).

For GUI cells specifically: scan-history JSON must parse with `scan_id` + `started_at_unix` + `completed_at_unix` + `completed_at_unix >= started_at_unix` — defends against fast-GUI-crash false-GREEN (positive elapsed without completed scan).

## 6. Verdict Interpretation Framework

After matrix lands, interpret per the following decision tree:

### 6.1 GREEN (<=1.10x)

Ship. v0.3.40 candidate meets criteria. Tag-cut + GH auto-promote per locked dev loop.

### 6.2 EDGE (1.10x-1.20x)

Inspect perf-startup decomposition + perf-rayon-hash + perf-chunks:

- **One named bucket dominates startup or engine work** (e.g., catalog_spawn_ms > 5s, or per-worker active_pct < 70%): targeted Phase 5+ fix. Engine ships fix in separate PR; matrix re-fires; verdict re-evaluates.

- **Residual >> sum(named buckets)** (sprint baseline: 4000x ratio): structural-bound startup. Per `feedback_dev_loop_matrix_canonical_pr_first` section 12.4 methodology-gap: revise criterion using structural-startup carve-out (§2.3). v0.3.40 ships as Phase-4-only OR Phase-N at acknowledged structural bound; v0.3.41 lazy-eframe-init scoped.

- **Defender-on cell exceeds 1.10x while Defender-off GREEN**: file methodology gap (§2.4 criteria-relative bound). v0.3.40 ships if Defender-off is canonical; gap drives v0.3.41+ matrix shape evolution.

### 6.3 RED (>1.20x)

Cycle. Engine investigates per perf decomposition; profile-first per Option A discipline (`feedback_dev_loop_matrix_canonical_pr_first` section 12.4 + sprint precedent on aa140a8 / b680354 pattern-match misses).

**EXCEPTION — structural-bound runtime carve-out** (per §7.8 Phase 10 discovery):

If the matrix verdict is RED >1.20x AND **all** of the following hold:
- Dominance check (§4.2) confirms the engineering-fixable bucket was already addressed by the prior phase (e.g., chunk_emit reduced via background-thread offload + rate-limit; checkpoint_save now `<5%` of original cost).
- Remaining gap is in a code surface NOT engineering-fixable in current scope (e.g., per-worker hash overhead in GUI process vs CLI process at parity worker counts).
- Multi-run aggregate (§7.6 mitigation) confirms tight variance band around the RED ratio (structural floor, not single-run noise).

Then: **ship at honest measurement + file methodology gap + scope next-version fix** (same spirit as §6.2 path 2 structural-startup carve-out, applied to runtime per-worker overhead instead of startup).

v0.3.41 ship outcome demonstrates this path: §2.1 = 1.385x mean of multi-run aggregate; checkpoint_save addressed; remaining 1.46x per-worker hash gap at N=16 workers parity is structural; ship + v0.3.42 per-worker investigation scope.

### 6.4 ERROR (sentinel)

Matrix runner bug or binary regression. Investigate runner first (defense-in-depth F1 + Cat 1 #1 layering); then engine regression test.

## 7. Sprint Methodology Lessons

Lessons surfaced by the v0.3.40 chain that informed this spec:

### 7.1 Multi-reviewer PR-first catches ship-safety bugs pre-merge

PR #167 cycle caught 7 ship-safety bugs in 1 cycle (quality F1 + F2 + F3 + F4 + F5 + codex Cat 1 #1 + #2 + #3). Without multi-reviewer pattern, matrix could have produced false-GREEN (F1 + Cat 1 #1), bricked workstation Defender state (Cat 1 #2 / F3), contaminated results (Cat 1 #3), or failed silently on CLI process failure (F1).

Reference: `feedback_dev_loop_matrix_canonical_pr_first`.

### 7.2 Multi-reviewer extends to interpretation-correctness pre-data

Multi-reviewer discipline catches not just code-correctness bugs but also DECISION-FRAMEWORK correctness BEFORE matrix data arrives. PR #170 cycle: quality reviewer caught engine's N3 interpretation framing (`groups_orphan > 0 = pool regression`) was wrong (it's normal `install()`-caller participation; sum-conservation invariant is the real plumbing check). Engine pushed 288edd2 with corrected guidance + added N4 throughput caveat (bytes is `g.size` not bytes-read; per-worker comparison VALID, absolute disk-MB/s NOT) + N5 idle_gap_ms derived metric. Without N3 correction pre-data, matrix data would have been misread as "no contention" when really "no rayon contention but emit cost is the actual surface."

Pattern: PR-first + multi-reviewer extends beyond "is the code right" to "is the decision-framework right." Both layers matter.

### 7.3 Profile-first prevents pattern-match misses

aa140a8 (runner-thread channel decouple when channel was already healthy) + b680354 (par_iter on emit when hash appeared to be the 2.39x cost) were both blind-swing implementations that missed the actual cost surface. Engine self-corrected by adopting Option A profile-first for Phase 5 (PR #170 rayon instrumentation FIRST; targeted fix SECOND commit informed by data). Pre-stated decision tree in PR description prevents post-hoc rationalization.

Phase 5 instrument matrix (03af877) then revealed yet a third blind-swing trap that profile-first prevented: the "hash 2.39x slower" attribution from a66f813 was itself variance-driven (see §7.6). Without PR #170 instrumentation, engine would have shipped a rayon-contention fix that would not have addressed the actual cost (emit, 22.3s in GUI / 0s in CLI single-shot). Profile-first saved a third pattern-match miss.

### 7.4 Structural-bound surfaces should be explicitly scoped

When residual >> sum(named buckets) in instrumentation decomposition, the cost is in code outside the engineering-fixable scope (e.g., eframe internals). File methodology gap + ship at honest measurement + scope next-version fix. Don't blind-swing at structural-bound.

v0.3.40 ship outcome demonstrates the pattern: §2.1 engineering-fixable ratio 1.055x GREEN; structural-bound residual 6.87s (3400x ratio vs sum_named 2.197ms); v0.3.41 lazy-eframe-init scoped to close residual.

### 7.5 Cross-routing discipline tightens coordination latency

Design's cross-routing commitment (PR #168 head-changes within 5min of engine post) tightened from 30min late backfill to 12sec same-channel-or-better cross-route across sprint. Pattern-level discipline pays off in coordination.

### 7.6 Single-run matrix variance can drive false-attribution

a66f813 Mick-corpus matrix produced cold-CLI 18.16s + cold-GUI 62.81s = 3.46x ratio, framing the gap as "engine-in-GUI 2.39x hash slowdown." 03af877 Phase 5 instrument matrix produced cold-CLI 38.82s + cold-GUI 47.84s = 1.232x raw / 1.055x engineering-fixable. The a66f813 CLI was an OUTLIER (Mick-corpus cold-CLI sprint band: 25-38s). The 3.46x attribution was variance-driven; HASH is actually FASTER in GUI (8 workers / 18.7s vs CLI 4 workers / 34.1s = 1.83x faster); EMIT (22.3s in GUI; 0s in CLI single-shot) is the actual cost.

Pattern: single-run matrix ratio interpretation is fragile when CLI denominator has measurement variance. Profile-first instrumentation rescued the chain by surfacing per-worker data that contradicted the variance-driven attribution.

**Source correction (2026-06-07 Phase 8 discovery):** the initial v0.3.40 spec drafting attributed the 14.33–48.26s Mick-corpus cold-CLI variance band (sprint range 3.4x) to page-cache lottery. Phase 8 of the v0.3.41 cycle revealed the actual source: `default_io_threads` probe non-determinism. Same binary, same corpus, different runs sampled 4–16 rayon workers; the 3.4x worker ratio explains the 3.4x wall variance exactly. Page-cache effects exist (see §7.10 first-run cold-purge anomaly) but were not the dominant source. §7.7 documents the engineering fix.

**Mitigations:**
- Repeat-measure when ratio is borderline before swinging at instrumentation scope-out.
- Treat single-run "RED at X.Yx" verdict as provisional until per-worker data confirms the cost attribution.
- Profile-first discipline is the right rescue: empirical decomposition catches both variance illusions AND actual cost surfaces.
- **Verify env-pin honored (§4.3):** matrix verdict reports MUST surface `num_workers` for the CLI cell AND the GUI cell. Asymmetric values are the canonical signal that the io_threads probe is still active (env pin missing or pre-empted by the OnceLock cache).

Concrete sprint evidence the profile-first + multi-reviewer disciplines compound to prevent ship-safety regressions.

### 7.7 Probe-once-cache + env override for cross-process determinism

`SUPERDEDUPER_FORCE_IO_THREADS=N` env override (PR #175 δ) + `OnceLock`-cached probe (PR #175 γ) together enable matrix testing with deterministic worker counts across separate processes. Pattern applicable to any engine-level perf control that:
1. Is non-deterministic per-invocation (sampling, probing, heuristic selection).
2. Must compare cleanly across CLI vs GUI processes in matrix verdicts.

**Two-layer architecture:**
- Within-process determinism: `OnceLock` caches the first probe result; every subsequent call in the same process returns the same value. Closes the GUI multi-scan-within-session variance.
- Cross-process determinism: env override read BEFORE the OnceLock probe path. Matrix harness pins the value (`SUPERDEDUPER_FORCE_IO_THREADS=16` canonical) for all cells in a verdict. Closes the CLI-vs-GUI process-pair variance.

Mirror existing `perf_instrument_*_enabled()` OnceLock surfaces. Add `read_<env>_env()` helper for parsing isolation. Test with `_serial_env_guard` Mutex for 2024 edition unsafe `set_var` safety in parallel test threads.

### 7.8 Structural-bound carve-out applies to runtime per-worker overhead, not just startup

v0.3.40 §6.2 EDGE handling explicitly carved out STARTUP structural bound (eframe/winit/egui first-frame init dominates GUI launch overhead; not engineering-fixable in current scope; queue for next-version lazy-init).

v0.3.41 Phase 10 discovery extends the pattern to RUNTIME per-worker overhead. At parity worker counts (N=16 both cells via §7.7 env pin), GUI hash work is 1.46x slower than CLI hash work — per-worker hash overhead inside the GUI process beyond what io_threads tuning, chunk_emit batching, or rate-limit can address. Sources are sprint-pending: GUI runner thread CPU contention, cache pressure from concurrent GUI rendering, shared-state mutex overhead in hash dispatch, bg-emit thread overhead beyond rate-limit.

**Same spirit as §6.2 path 2:**
- Profile-first instrumentation confirms decomp complete + dominance check rules out engineering-fixable bucket.
- Multi-run aggregate (§7.6 mitigation) confirms tight variance band around the structural floor.
- Ship at honest measurement + file methodology gap + scope next-version fix.

v0.3.41 ship outcome: §2.1 = 1.385x mean of 5-run aggregate (std-dev ~0.06, runs 2-5 tight band 1.292–1.435x); checkpoint_save addressed by Phase 4 bg-thread + Phase 7 rate-limit (chunk_emit -94%); remaining 1.46x per-worker hash gap is structural; ship + v0.3.42 per-worker investigation scope. §6.3 RED handling extended to formalize this carve-out path.

### 7.9 Instrumentation PR requires runner-side lockstep update

Each engine PR that adds instrumentation (new `perf-*:` emit lines, new `SUPERDEDUPER_PERF_INSTRUMENT_*` env vars, new env-controllable perf knobs like `SUPERDEDUPER_FORCE_IO_THREADS`) requires a matching matrix-runner update **in lockstep**:
- Harvest regex must EXPLICITLY enumerate the new prefix. The generic substring `perf-chunks` does NOT match `perf-chunk-emit` (verified empirically; runs would silently drop the new lines).
- Env gate variables must be set by the runner template (per-cell auto-set) before binary launch.
- Verdict report shape must include new fields surfaced by the instrumentation (e.g., `num_workers` per cell from `perf-rayon-hash` for §4.3 env-pin verification check).

v0.3.41 cycle landed 5 runner hotfixes (`da05506` CLI schema + `264d588` RAYON env+harvest + `2e03487` perf-chunk-emit harvest + `9a7b82f` CHUNK_EMIT env + `9d679e7` FORCE_IO_THREADS env pin). Each hotfix tracked an engine PR's instrumentation evolution. Pattern: when a Phase N instrumentation PR opens, the matrix runner needs the matching harvest regex + env var setting + verdict report extension before the cross-build matrix can fire usefully.

**Discipline:**
- Pre-cross-build: read the engine PR body's "instrumentation env vars" and "emit format" sections. Verify the matrix runner template has both the env-var setting and the harvest regex coverage.
- Post-fire validity check: confirm the new perf-* lines appear in the harvest output before interpreting the verdict. Silent drop = false signal.

### 7.10 First-run cold-purge yields colder disk state than subsequent runs

Sdd-testwin's 5-run multi-run matrix on 5c59624 revealed a subtle methodology artifact: run 1 cell1 cold-CLI was 16.80s while runs 2–5 mean was 11.53s (+5.26s on run 1). `sdd-standby-purge` frees RAM but does not necessarily evict the filesystem-level disk cache; subsequent runs in the same matrix session benefit from accumulated filesystem warmth.

GUI cells were minimally affected (cell2 run 1 20.95s vs runs 2-5 mean 20.16s; std-dev 0.65s). Engine work inside the GUI process is dominated by hash + emit (`chunk_loop`), not by inventory-stage page-cache state. The cold-CLI cell is the more sensitive surface because its single-shot wallclock includes more file inventory work proportionally.

**Mitigations:**
- When running multi-run aggregates for variance characterization, treat the first run's cold-CLI wall as suspect.
- Aggregate-with-exclusion (e.g., runs 2-N std-dev) is the load-bearing distribution metric; all-N std-dev surfaces first-run cold-purge anomaly as a tail.
- Single-run matrix verdicts that land near the §2.1 threshold should be cross-checked against multi-run aggregate to disambiguate first-run cold-purge from structural floor.

### 7.11 Lifecycle decomposition diff test prescribes drill-down surface

PERF_METRICS.md TTWS/TTW/TTDD 3-metric framework (PR #177; always-on per Mick directive 2026-06-07 08:25 PDT) is the canonical scan-lifecycle decomposition for CLI-vs-GUI diff investigation. Pattern:

1. **Compose:** `total_ms ≈ ttws_ms + ttw_ms + ttdd_ms` (duration sum per §4.3 invariant; small drift from per-phase `Instant::now()` granularity acceptable). Sanity-check on every cell.
2. **Diff:** subtract CLI durations from GUI durations field-by-field (`ttws_gui - ttws_cli`, `ttw_gui - ttw_cli`, `ttdd_gui - ttdd_cli`). Each field delta isolates which phase carries the gap.
3. **Drill:** dominant phase delta determines the next instrumentation/investigation surface.

Phase 11a (53843b1) verdict demonstrated the pattern. CLI durations: `ttws_ms=27 ttw_ms=406 ttdd_ms=14669 total_ms=15102`. GUI durations: `ttws_ms=243 ttw_ms=743 ttdd_ms=17114 total_ms=18100`. Field deltas (GUI − CLI): TTWS_diff +216ms (small), TTW_diff +337ms (small), **TTDD_diff +2445ms (~82% of ~3.0s total gap)**. Dominant phase identified → drill into hash + emit sub-phases (the +2445ms TTDD divergence localized the v0.3.41 Phase 10 hypothesis; see §7.13 + §7.14 for the resolved interpretation — what looked like a structural per-worker overhead was actually engineering-fixable chunked-dispatch overhead).

**Mick-corpus DIFF test discipline:**
- Paired single CLI+GUI cell on same corpus, same machine, same env pin.
- Defender state: off for canonical decomposition (matches §3 5-cell shape Defender-off cells).
- 2-cell shape sufficient (not 5-cell); §6 interpretation tree drives next-step routing.
- §7.6 CLI variance still applies to raw §2.1 ratio interpretation; the lifecycle DIFF is INDEPENDENT of ratio noise (each phase delta is a direct measurement, not a ratio).

The lifecycle decomp is THE prescribed first-step investigation for any future GUI-CLI gap surfacing on Mick-corpus or other production-corpora.

### 7.12 Hypothesis rule-out via in-binary control variable

When a hypothesis can be tested by toggling a single binary-or-environment control (e.g., minimize the GUI window to disable rendering), a single-cell paired DIFF test on the same binary delivers a decisive answer in matrix-wall time.

Phase 11b (2026-06-07 10:25 PDT) ruled out rendering contention as the source of TTDD divergence in **7 minutes wall**: `Win32 ShowWindowAsync(hwnd, SW_MINIMIZE)` called at +3.0s wall; ~17.5s minimized execution covered the entire dedupe/hash phase; GUI `ttdd_ms` was ~+5% LONGER minimized vs normal-window (within noise; signal: "essentially unchanged"; direction OPPOSITE the contention hypothesis prediction).

**Pattern:**
- Identify a hypothesis with a binary-or-environment control that can be flipped without rebuilding.
- Same binary, same corpus, same env vars, same matrix-runner; ONE difference.
- Compare against baseline normal-run cells.
- Decisive direction-of-change interpretation: matching prediction → confirmed; opposite or null → ruled out.

Use cases beyond rendering:
- Background-thread on/off via env var → tests bg-thread contention.
- Specific feature toggle via env var → tests that feature's contribution.
- Window state, file-system layer (USB vs internal), io_threads count, etc.

Faster + lower-cost than instrumentation builds for hypothesis-test phase. Should be the FIRST step before opening a heavier sub-instrumentation PR.

### 7.13 Structural-bound carve-out is a HYPOTHESIS not a conclusion

v0.3.41 §7.8 framed the per-worker hash overhead at parity workers (Phase 10 1.46x) as a "structural-bound runtime carve-out" — analogous to v0.3.40 §6.2 path 2 startup carve-out — and design ratified the framing for ship-decision purposes per §6.3 RED structural-bound runtime path.

Phase 11d (2026-06-07 12:25 PDT) **invalidated the structural-bound framing for the v0.3.41 Phase 10 residual specifically.** The +2108ms TTDD gap was NOT structural per-worker hash overhead; it was chunked-dispatch overhead, engineering-fixable via single-chunk pivot (`chunk_groups(laid, 1, usize::MAX)` at live.rs:1085). Phase 11d §2.1 = 0.710x SOLID GREEN with paired ratio 0.988x (GUI actually FASTER than CLI on this run).

**Methodology lesson:** structural-bound carve-out is the right tool for SHIP-DECISION ergonomics (don't block a real engineering win on something hypothesized as not-fixable) — but the "structural-bound" label should be treated as a HYPOTHESIS, not a conclusion. Deeper investigation (lifecycle decomp + parallel code-read + hypothesis rule-out experiments per §7.11/§7.12) may reveal an engineering-fixable surface inside what looked like a structural floor.

**Discipline:**
- When §6.2 or §6.3 carve-out path is taken, queue an explicit next-version investigation that TESTS the structural-bound hypothesis (don't just queue the next-version target as accepted-bound).
- v0.3.41 ship-decision was still CORRECT given v0.3.41-era understanding; the methodology worked as designed (ship at honest measurement + scope next-version → next-version surfaces the engineering-fixable lever).
- The carve-out is a temporary frame, not a permanent ceiling.

### 7.14 Architecture elimination as a fix-surface category

Phase 11c Candidate+ (PR #178) chose to ELIMINATE the chunked-dispatch architecture rather than incrementally optimize within it. The single-line live.rs:1085 change `chunk_groups(laid, 32, chunk_max) → chunk_groups(laid, 1, usize::MAX)` collapsed the chunk loop to one iteration; the io_pool.install + par_iter dispatch fires ONCE over the whole corpus (CLI parity). Supporting infrastructure: SaveWorker bg-thread auto-flush timer (preserves crash-recovery window) + `Arc<Mutex<Checkpoint>>` migration (11 sites) for cross-thread snapshot access.

**Pattern:** when sub-phase investigation surfaces an architectural overhead (per-iteration dispatch cost, lock contention from architecture, contention from architecture-mandated background threads), the fix surface may be "don't do this architecture; do CLI's architecture" rather than "optimize within current architecture." The v0.3.41 chunk_emit instrumentation + Phase 4 bg-thread + Phase 7 rate-limit + Phase 9 probe stabilization were all incremental within-architecture optimizations; v0.3.42 Phase 11c eliminated the architecture entirely.

**Discipline:**
- After incremental optimizations exhaust within-architecture leverage, ask: "what if we eliminate this architecture entirely?"
- Cross-check by comparing CLI's architectural choices (especially when CLI is the reference and GUI is the divergent path).
- Architecture elimination is a STRUCTURAL FIX not an incremental optimization; the methodology compounding from prior phases identifies the surface even if no prior phase touched it directly.

v0.3.42 ship outcome demonstrates: 6 sdd-testwin runner hotfixes + 7 engine/overflow PRs across v0.3.40+v0.3.41+v0.3.42 cycles collapsed to a single architectural change (Phase 11c chunk_groups N=1 + supporting Mutex migration) + a 2nd-tier supporting timer infrastructure (SaveWorker auto-flush). The compounding instrumentation made the surface VISIBLE; the architectural choice made the fix POSSIBLE.
